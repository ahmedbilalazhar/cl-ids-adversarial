# Capture context and generalization

## A stage is also a capture context

The proposed E1-E4 schedule follows Tuesday-Friday family availability. New-family identity, capture day, scripted traffic context and stage position therefore change together. The paired clean/poison comparison estimates the poisoning effect under this fixed trajectory; it does not independently estimate the effects of class arrival, temporal drift, stage order or a different operational network.

Do not describe positive acquisition as general temporal adaptation without additional evidence. Do not describe post-E2 changes as a pure time-decay effect: additional training, new labels and new background distributions occur simultaneously. Matched clean trajectories control their common contribution to the declared clean-subtracted endpoint, but do not make the mechanism universally identified.

## Components do not isolate hosts or campaigns

The endpoint-pair/protocol session rule separates operational sessions. It permits the same hosts, endpoints and scripted attack campaign to appear in different model roles through separate components. Content isolation removes exact representational overlaps; it does not remove near-duplicates, shared host fingerprints or campaign context.

Report source day/window coverage, endpoint concentration, component sizes and role-level host/pair overlap. Describe the result as component-isolated within-capture evaluation. Never call it host-disjoint, campaign-disjoint or cross-organization evaluation unless an additional design actually enforces that boundary.

A host/campaign-disjoint split could make some families unlearnable because the benchmark has few attack realizations. That is a limitation to expose, not a reason to repeatedly search splits or weaken support checks until the table passes.

## Observed context concentration in the screened corrected candidate

The complete retained Hulk inventory (158,468 records) and FTP-Patator inventory (3,972 records) each use one unordered endpoint-pair/protocol key, shared across train/development/test. The fixed test and training roles share 21,653 such pair keys and 10,444 hosts overall. This coexists with zero shared session/content components. It directly establishes that this candidate is not host- or endpoint-pair-disjoint. Pair keys are not campaign identifiers, and concentration does not itself prove a learned shortcut. ## Bounded additional evidence, only for claims that need it

- **Source-artifact diagnostic:** select any feature-group ablation from source/extractor rationale before final outcomes, retune only as predeclared, and label the changed schema. Do not drop features after inspecting final importance/accuracy. This supplements the primary 76-feature study; it does not silently replace it.
- **Order diagnostic:** swapping the two post-E2 arrival blocks would be an artificial schedule sensitivity, not preserved capture chronology. At five core arms, clean/maximum dose and twelve seeds, it adds 120 new E3/E4 suffix executions if E1/E2 parents can alias exactly. It is outside the base package and does not create independent captures.
- **Independent capture:** a separately audited source with a justified source family, compatible question and frozen analysis provides stronger transport evidence. It requires its own feature/schema/stage/support contract; do not pool its estimates automatically.

Prioritize the approved primary data, correct engine, paired replication and an informative result over running all optional diagnostics. If resources are constrained, state the unresolved scope clearly. A narrow reproducible finding is useful without claiming general deployment validity.

## Claim wording

Use: "Under this fixed component-isolated CICIDS2017 class-arrival simulation, we observe ..." followed by the actual magnitude, uncertainty and conditions.

Avoid: "The defense handles real-world concept drift," "generalizes to unseen organizations," "recovers naturally with time," or "prevents successful Hulk DoS" on the evidence planned here alone.

This follows the broader need to align security-ML evaluation with its actual sampling and deployment question. [Arp et al., USENIX Security 2022](https://www.usenix.org/conference/usenixsecurity22/presentation/arp).
